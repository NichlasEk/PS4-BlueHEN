IMPLEMENTED
research/native-probe/probe.c is a bounded inventory payload:
- Firmware information; refuses further inventory unless version is 9.60.
- Current-process module names and named export resolution only.
- Candidate device/library names in /dev, /system/common/lib, /system/priv/lib.
- Append log: /data/bluehen/native-probe.log, fallback /user/data/bluehen/.
- No device opens, ioctl, scan, pairing, Bluetooth reset, AudioIn call, PRX
  injection, module load or kernel patches in the probe itself.
- Only creates a log directory and appends the report. SDK startup/loader
  behavior is separate; this is not an assurance about an untested loader.
- Does not inspect modules in ShellCore, ShellUI or other processes. Missing
  exports in this inventory do not prove system-wide absence.

NATIVE TRANSPORT QUESTIONS
OpenOrbis BluetoothHid.h exposes only sceBluetoothHidGetDeviceInfo with no
useful parameter signature. That is not a raw HCI/L2CAP API.
The payload SDK includes stock FreeBSD Bluetooth headers; their presence does
not demonstrate PS4 kernel support. Do not blindly use FreeBSD protocol IDs,
device ioctls, guessed offsets or private function signatures on the PS4.
Determine ownership and ABI using actual 9.60 module evidence. Start with
metadata/export discovery, then local analysis of matching firmware modules
if available. Keep proprietary firmware and dumps local.
Need proof of an additional ACL/L2CAP link coexisting with DualShock input.
Do not detach/reset the internal controller as the first experiment.

MICROPHONE ARCHITECTURE AND ACCEPTANCE GATES
Playback: PS4 as A2DP Source -> compatible Sink; SBC baseline; negotiate
capabilities instead of hardcoding a brand/model whitelist.
Microphone: headset must expose a two-way profile (HFP is the initial target).
PS4 side must act as Audio Gateway: SDP/RFCOMM service-level connection,
codec negotiation and SCO/eSCO data transport in both directions. HearBridge
has no such implementation. HFP is separate from A2DP; an A2DP-only speaker
cannot supply a microphone. Simultaneous high-quality A2DP and HFP cannot be
promised for arbitrary headsets; explicitly design a voice mode and test it.

Required independent milestones:
1. Native transport access + controller coexistence, no audio needed yet.
2. SDP/capability discovery with at least one actual A2DP/HFP headset.
3. Low-volume SBC test tone -> A2DP playback -> one game's PCM.
4. HFP service-level connection -> SCO/eSCO transport -> bounded microphone
   PCM capture/level measurement in our own test application.
5. Real PS4 audio-input routing: getting PCM in our app is NOT party chat.
   Determine AudioIn/service routing and ABI before writing an injection path.
   Upstream AudioIn headers list names with void() placeholders, not usable ABI.
6. A remote chat participant confirms live speech; test mute, user assignment,
   disconnect/reconnect, controller continuity, latency and audio quality.
7. Broaden interoperability across headset vendors/profile versions. Do not
   claim 'every generic sink' from one successful headset.

Until steps 1 and 5 have a verified route, native audio+mic remains feasibility
work. No UI toggle or advertised HFP service should claim working microphone
support before the corresponding transport and audio routing are implemented.
