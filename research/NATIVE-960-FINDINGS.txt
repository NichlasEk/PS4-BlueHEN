Native Bluetooth / microphone findings, 2026-10-24

CURRENT CONCLUSION
There are real system Bluetooth audio paths and a virtual microphone API in
the examined 9.60 firmware. These are useful research leads, not proof that
generic A2DP/HFP devices work. No native headphone or microphone support has
been enabled by this branch.

LIVE EVIDENCE
The user-selected console returned firmware_raw=960 from ps4debug-NG 1.3.2.
FTP was already active. Remote receiver HTTP service was not running.
The known debugger was started using the exact pinned payload SHA-256:

Its version response then verified execution. No empty binloader probe was
sent. Subsequent debugger commands only queried metadata and read memory;
no RPC stub, allocation, call, patch or register modification was performed.

Observed device node names: /dev/bt, /dev/wlanbt, /dev/bluetooth_hid, /dev/hid.

orbis_audiod has a /vmicDdShmAin mapping.
No Bluetooth scan, pairing, disconnect or reset was requested.
No headset microphone stream or voice data was read/recorded.

BLUETOOTH HID LAYER
libSceBluetoothHid.sprx SHA-256:
e54ba1a91625f2ec3b657bf33d5ba456eef8bce8b02a8f7206c9e39c3deddadb
17 defined symbols; known names can be recovered by matching Orbis NIDs.
Matched names include Init, RegisterCallback, UnregisterCallback,
RegisterDevice, UnregisterDevice, GetDeviceName, GetReportDescriptor,
GetInputReport, GetFeatureReport, SetOutputReport, SetFeatureReport,
DisconnectDevice and GetDeviceInfo under the sceBluetoothHid prefix.
Do not confuse these HID operations with a generic audio profile interface.

GetDeviceInfo at offset 0x1400 prepares a 16-byte ioctl envelope with an
integer argument and a pointer, then uses request 0x8010a40b against the HID
device path. The size/meaning of the pointed-to output is not recovered.
No query using that guessed structure has been attempted.

AUDIO DAEMON BLUETOOTH PATH
orbis_audiod contains an AVDTP error-name table. This table alone cannot prove
that a usable A2DP profile implementation is active or complete.
Separate code opens /dev/bt for audio output and audio input.
Observed request constants include 0x80106212, 0x80206216 and 0x80206217.
The receive path using 0x80206217 leads to a sceBtRecvAudio error message and
JEDI processing at 16/48 kHz. This suggests the existing controller audio
path; generic HFP/SCO behavior is not established. Do not replay these ioctls
or assume a PCM buffer layout from the request's encoded envelope size.
Further work must trace device identification, profile setup and actual
payload encoding before deciding whether to reuse any of this path.

VIRTUAL MICROPHONE CANDIDATE
Exact NID matches in the 9.60 AudioIn module:
  sceAudioInVmicCreate   DVTn+iMSpBM  offset 0x2840, size 309
  sceAudioInVmicDestroy  3ULZGIl+Acc  offset 0x2980, size 222
  sceAudioInVmicWrite    4kHw99LUG3A  offset 0x2b80, size 413
The same names/NIDs appear in shadPS4's source, but those functions are stubs
there. Its void-argument declarations are not evidence of the console ABI.

Static observations, NOT a callable ABI contract:
- Create preserves argument registers esi, edx and ecx across initialization.
- It accepts esi values 128 or 256 and edx values 16000 or 48000.
- Its ecx check accepts 0..2, with 0 normalized to 1.
- Write uses edi as a handle-like value, esi as a count and rdx as a pointer.
- Write checks esi <= 1024, handle prefix 0x00040000 and slot range 0..3.
- Write computes a byte count as esi * a stored field * 2 and caps it at 4096.
- It uses a shared-memory/event-flag path and a wait value of 2000000.
The first Create argument's semantics, permission requirements, the stored
field's meaning, routing and exact wait behavior still require verification.
Do not call these functions in PartyDaemon merely because they are mapped.

SAFE NEXT EXPERIMENT DESIGN
Finish the initialization and service-call analysis. Then a dedicated,
removable test application can attempt virtual-mic creation, write bounded
synthetic silence and destroy only its own returned handle. It must not alter
global input routing or existing microphones as an initial test. An API return
code is not chat proof: later acceptance requires the intended user/input to
be selected and a remote participant to confirm real microphone speech.

The independent radio gate remains: generic headset discovery/SDP,
ACL/L2CAP/AVDTP for A2DP, RFCOMM/HFP plus SCO/eSCO for mic, all coexisting
with the DualShock. Do not substitute the workstation USB dongle for this.
